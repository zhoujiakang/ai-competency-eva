# AI 能力测评系统 · 重敲方案

> 目标：把现有 AI 生成的项目，重建成一个「每一行都自己写过、git 历史可讲、
> 可以直接开源、能写进简历」的版本。

## 一、先体检：你要重敲的到底是什么

### 规模

| 模块 | 行数 | 文件数 | 说明 |
|---|---|---|---|
| `backend-java` | 2263 | 71 | Spring Boot，47 个 REST 接口，9 Controller / 7 Service / 17 Mapper / 16 Entity |
| `agent-python` | 4599 | 56 | FastAPI + LangGraph，出题 / 追问 / 评分 / 收尾，14 个测试文件 |
| `frontend-ai-assessment` | 7084 | 26 | React 19 + Vite（其中 `styles.css` 占 2375 行，JSX/JS 约 4700 行） |
| `database.sql` | 384 | 1 | 幂等建表 + 增量迁移 |
| `docs/` | 2737 | 7 | 设计文档（这是本次重敲最大的资产，见第三节） |

合计约 **1.4 万行源码**。按每天 2~3 小时、200~300 行有效产出算，纯敲打周期约
**8~10 周**，加上开源化与简历包装，按 **10~12 周**排。

### 现状里的几个问题（重敲前必须处理）

1. **git 历史基本没有价值**：全项目只有 6 个 commit，第一条 `feat: AI 能力测评系统`
   一次性提交了 177 个文件 / 16663 行。这条历史在面试里是负分项——它证明不了过程。
2. **有 50 个文件、+4443/-575 的改动没提交**：工作区里躺着一版比 master 更新的代码。
   重敲之前必须先落地，否则重建过程中这版会被覆盖丢失。
3. **不能直接开源的三处**：
   - `deploy/release.sh:18` 与 `README.md:92` 硬编码了生产服务器 IP `120.26.93.206`；
     README 里还提到同一台机器上「朋友的静态页」——这是别人的东西，不能公开。
   - Java 包名 `com.huiqiyikang.assessment` 带公司/组织痕迹，个人项目建议改成
     `io.github.<你的用户名>.assessment`。
   - 仓库里没有 LICENSE。
4. **好消息**：密钥是干净的。`.env` 从未进入任何一次提交（已核对全部历史），
   首次提交里出现的 `sk-xxxx` 只是 `.env.example` 的占位符。不需要 rewrite history，
   也不需要轮换密钥。

## 二、策略选择：三种「重敲」，选哪一种

| 方案 | 做法 | 耗时 | 简历价值 | 结论 |
|---|---|---|---|---|
| A. 逐字重打 | 对着原文件一行行敲 | 10 周+ | 低 | ❌ 只是抄写，遇到报错仍然不会，面试问深了就露 |
| B. **照着文档重写实现** | 把 `docs/` 当规格，关掉原代码自己写；写完再 diff 原实现做验收 | 8~10 周 | 高 | ✅ **推荐** |
| C. 保留代码只补规范 | 不动代码，补 CI / LICENSE / 文档，重建历史 | 1~2 周 | 中 | 🔸 保底方案，可先做，但"重敲"这件事没有发生 |

**为什么选 B**：A 和 B 打出来的字一样多，区别在于**信息来自哪里**。
A 的信息来自屏幕上已有的代码（抄），B 的信息来自文档和接口契约（设计）。
只有 B 能让你在面试里回答"这里为什么这么设计"。

如果 10 周太长，可以 **C 打底 + B 增量**：先花一周把开源化和规范补齐（让项目至少是个
拿得出手的仓库），之后每周重写一个模块替换进去——旧文件删掉，新文件是自己写的。

## 三、核心方法：文档即规格，代码只做验收

`docs/` 里已有 2737 行设计文档（整体功能 / 模块架构 / Agent 设计 / 画像模块 / 功能清单）。
这是绝大多数项目没有的资产——**它就是你的需求规格书**。

### 三条铁律

1. **写的时候只开文档，不开原代码。** 屏幕左边是 `docs/模块设计架构文档.md`，
   右边是空的编辑器。卡住了怎么办？先猜、先写错、先跑起来看报错——这是重敲唯一的价值来源。
2. **一个模块写完再 diff。** 用 `git diff` 或并排对比原实现，只看两件事：
   我漏了哪个边界情况？我的写法哪里更好？把结论写进当天的 commit message 或笔记。
3. **每个模块先写测试再写实现。** `agent-python/tests/` 已有 14 个文件可以当测试规格；
   后端和前端测试很少，正好由你补齐——补测试本身就是简历素材。

### 自检：我是真在重敲，还是在抄写？

- 关掉原代码后，我能不能说出这个模块的输入、输出、失败路径？
- 我写的实现和原实现不一样的地方，我能不能解释为什么我的更好？
- 这个模块的 commit message 我能不能不看代码就讲出"为什么改"？

三个都答不上，说明这段白敲了，回退重来。

## 六、Git 规范

### 6.1 分支模型：trunk-based + 短分支

单人项目不要搞 git-flow（develop/release/hotfix 那一套对一个人是负担）。

```
main                     ← 永远可运行、可部署，受保护，只接受 PR
  ├─ feat/agent-scoring       ← 一个功能一条分支，1~5 天
  ├─ fix/sse-buffering
  └─ chore/ci-gitleaks
```

规则：

- 分支名 `类型/简短英文描述`，全小写连字符：`feat/`, `fix/`, `chore/`, `docs/`, `refactor/`, `test/`
- 分支存活不超过 5 天，`main` 上永远可运行
- 合并用 **squash merge**（历史线性、一个功能一条 commit）或 rebase，**不要 merge commit**
- 合并后立刻删远端分支
- 加 tag 时才代表"发版"：`v0.1.0`、`v0.2.0`……（SemVer）

### 6.2 Commit 规范：Conventional Commits

格式：

```
<type>(<scope>): <subject>

<body：为什么这么改，而不是改了什么>

<footer：Closes #12 / BREAKING CHANGE>
```

`type` 取值：`feat` `fix` `refactor` `test` `docs` `chore` `perf` `build` `ci` `style`

`scope` 用模块名：`backend` `agent` `frontend` `db` `deploy` `ci`

正例（中文 subject 完全可以，保持全程一致即可）：

```
feat(agent): 按考察点权重选取下一题

原先按顺序取题，学生在某一维度连续得分偏高时会反复问同一维度，
题量浪费在已掌握的能力上。改成按维度缺口加权随机，
缺口越大被抽中的概率越高。

Closes #18
```

```
fix(frontend): 登录页只有表单区滚动，左侧品牌区固定
```

反例（你现在仓库里就是这样）：

```
feat: AI 能力测评系统（Java 后端 + Python Agent + React 前端 + Docker 部署）
  ← 177 个文件 / 16663 行。这条 commit 讲不出任何设计决策。
```

**粒度原则**：一个 commit = 一个「能编译 + 能过测试 + 一句话讲得清」的最小变更。
自己判断标准是——**能把这条 message 倒过来写成一条 issue 标题**。

不要出现 `wip`、`update`、`fix bug`、`改了一下`。

### 6.3 工具门禁（重敲第一天就装好）

| 工具 | 作用 | 配置位置 |
|---|---|---|
| `check.sh` | 三端测试 + lint + 生产构建，已有 | 仓库根目录 |
| husky + lint-staged | commit 前自动跑 lint / 格式化 | `frontend-ai-assessment/` |
| commitlint | 校验 commit message 格式，不合规直接拒绝 | 根目录 `commitlint.config.js` |
| gitleaks | 阻止密钥被提交（**开源项目必备**） | `.pre-commit-config.yaml` + CI |
| Dependabot | 自动更新依赖、开 PR | `.github/dependabot.yml` |
| 分支保护 | `main` 禁止直接 push，必须过 CI | GitHub 仓库设置 |

### 6.4 即使一个人，也要走 PR

理由不是流程好看，是它**逼你写一段自述**。每个 PR 描述固定回答三问：

1. 这个 PR 解决什么问题？
2. 我怎么验证它？（跑了什么命令、看到什么结果）
3. 有什么取舍或遗留问题？

这三问就是面试时被问到的形式。10 周后你手上会有 30+ 份 PR 记录，等于 30 份面试逐字稿。

### 6.5 历史重建建议

不要在原仓库上 `git rebase -i` 去改那 6 条 commit——收益低、风险高。直接**开新仓库**：

```bash
# 1) 旧仓库先冻结（保住现在这 50 个未提交改动）
cd ~/code/ai-competency-evaluation-system
git add -A && git commit -m "chore: 冻结参考实现（v0 归档）"
git tag v0-archive && git push origin master --tags

# 2) 开新仓库
mkdir ~/code/ai-assessment-v2 && cd $_
git init -b main
gh repo create ai-assessment --public --source=. --remote=origin

# 3) 第一条 commit 只放脚手架，不要抄旧文件
printf '# AI Assessment\n' > README.md
git add README.md && git commit -m "chore: 初始化仓库"
```

小步提交的做法：**先提交空骨架 → 再提交第一个能跑的最小版本 → 之后一个功能一条 commit**。
目标是让 `git log --oneline` 读起来像一份开发日志，而不是一份文件清单。

## 九、每天怎么干活

一个可重复的循环（每次 2~3 小时）：

```
1. 选一个模块  →  只打开 docs/ 对应章节 + 该模块的接口契约
2. 写测试      →  先写 1~2 个失败的测试，明确这个模块该干什么
3. 写实现      →  让它通过。卡住就猜、就跑、就看报错
4. 跑 ./check.sh
5. 对照原实现  →  只 diff 这一个模块，记录差异结论
6. git commit  →  按规范写 message，body 说清"为什么"
```
